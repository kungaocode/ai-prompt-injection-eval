2. TRAINING PROCESS AND CRITICAL TECHNICAL FIXES
------------------------------------------------------------

  2.1 Phase 1: Initial Training (Step 0 -> 2880, ~14 hours)
      Training started 2026-08-08. Model converged from loss 2.577
      (step 5) to 2.068 (step 2880). Eval loss: 2.335 -> 2.250.
      Training halted at step 2880 (epoch 1.32, 43.9% progress).

  2.2 Phase 2: Failed Resume Attempts (Multiple, ~12 hours wasted)
      Over the next 12 hours, multiple resume attempts were made.
      ALL of them failed silently: they loaded adapter weights
      correctly but RESET optimizer momentum, LR scheduler, global
      step counter, and RNG state to zero. Each restart trained from
      scratch on top of checkpoint-2880 weights, wasting GPU time
      and producing confusing logs (epoch always reset to 0.002).

  2.3 Six Critical Bugs Found and Fixed

      [Bug 1] Missing resume_from_checkpoint parameter
        Location:  train_qwen3_4b.py, resume_train.py
        Symptom:   Every restart began from global_step=0 despite
                   loading correct checkpoint-2880 adapter weights.
        Root cause: trainer.train() called without the
                   resume_from_checkpoint argument. Trainer only
                   restores optimizer/scheduler/step when this is set.
        Fix:       Changed to trainer.train(resume_from_checkpoint=...)
                   and added find_latest_checkpoint() for auto-discovery.

      [Bug 2] UnicodeEncodeError on Chinese Windows (GBK codepage)
        Location:  Multiple print() statements in training scripts
        Symptom:   Script crashed at print() with UnicodeEncodeError.
        Root cause: Used U+2022 (bullet) and U+2014 (em-dash) chars
                   that GBK cannot encode. Chinese Windows terminals
                   default to GBK codepage, not UTF-8.
        Fix:       Replaced all special chars with ASCII equivalents:
                   bullet -> [-], em-dash -> --.

      [Bug 3] transformers 5.14 requires torch >= 2.6 (CVE-2025-32434)
        Location:  Import chain of transformers/trainer.py
        Symptom:   ValueError: upgrade torch to at least v2.6
        Root cause: transformers 5.14.1 added check_torch_load_is_safe
                   requiring torch >= 2.6. CUDA 12.1 PyTorch wheels
                   only go up to torch 2.5.1.
        Fix:       Downgraded transformers to 5.13.1 via pip install.

      [Bug 4] torch 2.5.1 cannot load rng_state.pth (weights_only=True)
        Location:  transformers/trainer.py:_load_rng_state()
        Symptom:   _pickle.UnpicklingError on numpy dtypes at resume.
        Root cause: rng_state.pth contains numpy objects (_reconstruct,
                   ndarray, dtype, UInt32DType). torch 2.5.1 rejects
                   the entire numpy type chain. add_safe_globals fails.
        Fix:       Monkey-patched torch.load BEFORE all HF imports,
                   forcing weights_only=False for local checkpoints.

      [Bug 5] Hard-coded RESUME_CHECKPOINT path
        Location:  train_qwen3_4b.py configuration section
        Symptom:   Must manually edit source code to change step number.
        Fix:       Replaced with find_latest_checkpoint() that scans
                   OUTPUT_DIR for the highest-step checkpoint directory.

      [Bug 6] Loss log file overwritten on each run
        Location:  NaNGuardCallback initialization
        Symptom:   Fixed filename loss_log.csv destroyed previous data.
        Fix:       Timestamped filenames: loss_log_YYYYMMDD_HHMMSS.csv.

  2.4 Phase 3: Successful Resume and Completion (Step 2885 -> 6567)
      After all 6 fixes, training resumed from checkpoint-2880 on
      2026-08-09 02:27 and completed 3,687 remaining steps without
      further interruption. Total: ~26 hours for all 6,567 steps.

  5.2 Root Cause Chain
      1. Training set is small (~10M tokens) relative to model capacity
      2. Domain texts are highly specialized and contain repetitive patterns
      3. 3 epochs exposes model to ~30M effective tokens; it begins
         memorizing specific documents rather than learning linguistic
         generalization by epoch ~1.7
      4. Cosine LR decay to ~1e-11 prevents escape from local minimum
      5. Classic overfitting signature: train loss keeps decreasing,
         eval loss keeps increasing

  5.3 Recommendations for Future Runs
      - Use 2 epochs max, or implement early stopping on eval loss
      - Collect ~20-30M additional tokens of domain data
      - Increase LoRA rank to r=32 for more adapter capacity
      - Add data deduplication (cosine similarity threshold)
      - Consider constant LR instead of cosine schedule

     - NOT caused by data corruption or infinite model loops
     - All 25 samples evaluate correctly when run individually
     - Each sample processes in 0.16-1.10 seconds with valid loss
     - The hang was caused by GPU VRAM accumulation across three
       consecutive model load/unload/eval cycles without proper
       inter-cycle cleanup (gc.collect() + torch.cuda.empty_cache())
     - Fixed by serial evaluation with explicit GPU reset between models

7. KEY CONCLUSIONS
------------------------------------------------------------

  1. QLoRA fine-tuning on consumer hardware is demonstrably effective.
     Domain PPL improved 22-28% vs the base model across two independent
     evaluation settings. The model successfully absorbed CS, cryptography,
     and security domain knowledge from only 19K training texts.

  2. The best checkpoint is NOT the final model. Never skip checkpoints.
     checkpoint-3840 (epoch 1.75, 58.5% progress) is the optimal model.
     The final merged model is 7.5% worse. Without intermediate checkpoints
     saved every 480 steps, this project would have been a near-total
     failure -- the final model alone is substantially suboptimal.

  3. Three epochs is too many for ~10M tokens of specialized data.
     Overfitting begins at epoch ~1.7. Training loss continues decreasing
     (model memorizes better) while eval loss rises (model generalizes
     worse). Recommend 2 epochs or early stopping on eval loss.

  4. Data quality deserves as much attention as model architecture.
     ~16% of problematic validation samples are severely OCR-corrupted.
     They do not break training but inflate metrics and complicate
     debugging. Clean data = reliable experiments.

  5. Consumer GPU fine-tuning is a viable research methodology.
     Entire project completed on a single RTX 4060 8GB. Total cost:
     ~26 hours training + ~8 hours evaluation and debugging. Domain
     adaptation is accessible without cloud GPU rentals.

  6. The pipeline is fully reproducible and documented.
     All code, checkpoints, evaluation scripts, and logs are saved.
     The approach transfers to other domains, larger models, or
     different hardware with minimal modification.
